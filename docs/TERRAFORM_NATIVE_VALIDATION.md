# Credential-free native Terraform gate

Implementation/operation contract. The official two-platform provider lock was generated
in isolated CI, cryptographically checked and independently reviewed before being committed.
Only exact-head CI receipts establish full native execution results. Do not infer a passing
gate from the command descriptions below.

Phase1B-AWS-0R remediates tooling compatibility on the existing PR#6 branch. It
does not authorize AWS access, a plan, deployment or source-authentication promotion.
The starting approved head is6142c08b4a72412bb6674f46d06417c36bacb47f. Exact ending
head, native receipts, regression counts and fresh review are recorded on
[PR#6](https://github.com/farhan-shafee/cloudsecops-live/pull/6).

## Tool and artifact custody

The source and runner pin Terraform1.17.1 and registry.terraform.io/hashicorp/aws6.71.0.
Terraform1.17.1 is the stable release selected from the official install/release pages
on2026-11-03. The CLI has BSL1.1 terms; the provider is MPL2.0. Original harness and
test code remain MIT. No downloaded executable, public-key bundle or upstream
implementation belongs in Git.

The native job runs on disposable Ubuntu24.04 AMD64, using the existing reviewed
checkout/setup-python/upload-artifact commit SHAs and contents:read permissions.
It installs nothing globally and changes no workstation PATH, settings or trust store.
The Terraform CLI and provider do not run on the memory-constrained workstation.

Before any Terraform execution, the harness:

1. Downloads only fixed official HTTPS public-key, checksum, signature and archive URLs,
   with byte/time bounds, explicit CA verification and no ambient proxies.
2. Uses GnuPG in a new private home with no user options, automatic key retrieval or
   owner-trust changes. The full primary fingerprint is independently anchored to
   HashiCorp's security page and HCSEC-2026-03, not merely asserted by registry metadata.
3. Verifies both detached checksum-manifest signatures and compares both Linux AMD64
   and Windows AMD64 CLI/provider archive hashes to the signed manifests and reviewed
   source pins. The actual extracted CLI is selected by absolute path.
4. Requires a currently valid primary and actual selected signing key. HashiCorp's
   public bundle also contains a retired signing subkey; GPG can emit KEYEXPIRED for
   that unrelated key while validating a current signature. Only a timestamp explicitly
   bound to a known retired nonselected subkey is tolerated. Unknown warnings, expired
   selected keys, revocation, bad signatures or the wrong primary fail closed.

The original overly broad expiry-warning check failed before Terraform ran. Independent
machine-output regressions reproduced the distinction; this is not an exception allowing
an expired signing key. Small public-key/signature diagnostics were additionally checked
with the already installed GPG and a project-private keyring; no local Terraform/provider
execution or AWS activity was involved.

## Reviewed dependency lock

`.terraform.lock.hcl` is generated by the verified Terraform dependency mechanism:

```text
terraform providers lock -platform=linux_amd64 -platform=windows_amd64 registry.terraform.io/hashicorp/aws
```

This command installs no AWS resources and does not initialize/configure the provider.
The bootstrap emits a proposed lock but deliberately fails acceptance while the reviewed
committed lock is missing. Hash values are not hand-authored. Normal CI has no bootstrap
flag and requires the committed file before downloads or execution.

Review requires exactly the AWS provider/address/version/constraint, both platform package
bindings, and every zh checksum from the successfully verified publisher manifest. More
than two zh hashes are expected because the signed manifest covers other platforms too.
Two arbitrary h1 strings do not prove platform coverage: each normal job independently
reproduces the two-platform lock through the official registry and compares the normalized
result. A missing, changed or unexpected provider/lock fails.

## Native commands and isolation

Only reviewed main.tf.json and the committed lock enter a new validation directory.
The structural policy first rejects extra configuration, modules, data sources, backends,
provisioners, private variables and unexpected source files. The child environment is
constructed from an allowlist, without enumerating user environment secrets. HOME,
temporary files and CLI configuration are private; AWS config/credentials files are empty,
metadata discovery is disabled, and token/proxy/CLI-argument/cache/reattach overrides are absent.
The direct provider installation configuration permits only the pinned AWS source.

The fixed command set is version, fmt, providers lock, init, validate and providers schema.
No plan, apply, destroy, import, refresh, state, console or arbitrary argument/command path
is available. No AWS identity check is performed: validate/schema inspection use the
provider's schema protocol, not deployment configuration or cloud APIs.

After lock reproduction, native acceptance runs:

```text
terraform fmt -check -recursive -no-color
terraform init -backend=false -input=false -lockfile=readonly -no-color
terraform validate -json
terraform providers schema -json
terraform init -backend=false -input=false -lockfile=readonly -no-color
terraform validate -json
```

The installed Linux provider executable must match the executable streamed from the
independently verified official archive before validation/schema execution and again
after reinitialization. Lock changes and implicit updates fail. Validation needs a zero
exit, supported JSON format, valid=true, consistent zero error counts and complete
diagnostics. Non-JSON, contradictory or incomplete output is failure. Schema inspection
checks the real AWS provider and every used resource/argument/nested block; resource
schema migration versions are not mistaken for the provider release version.

Terraform fmt ignores .tf.json during directory scans. Its successful execution is a
no-op for main.tf.json, not JSON formatting proof. Native configuration validation is
the meaningful parsing/schema check; the Python structural policy remains independently
mandatory.

Receipts contain only source/input hashes, tool versions, publisher fingerprints,
verification statuses, validation counts and schema counts. Raw tool output and downloaded
executables stay in private disposable space. Explicitly allowlisted sanitized artifacts
expire after3days. The job asserts the checked-out Git SHA matches the workflow revision;
PR test-merge trees are reconciled to the reviewed feature tree separately.

## IAM, delivery and retention boundaries

The native schema is compatibility evidence, not effective authorization or successful
service delivery. BOE ownership is compatible with CloudTrail's bucket-owner-full-control
upload ACL; do not enable ACL ownership to work around it. Exact trail/account conditions
and regional log/digest prefixes remain. The TLS deny exempts AWS service principals as
recommended for service calls whose network context can be redacted; non-service callers
remain subject to the deny. Ordinary bucket names exclude reserved namespaces.

Collector/verifier reads and DescribeInstances-only test actions remain separate from
externally provisioned provisioning/cleanup authority. STS GetCallerIdentity needs no
permission grant; policy shape cannot constrain that API into proving region or expiry.
Those remain separately bound client/provider observations. No AdministratorAccess fallback,
new runtime role, credential or policy attachment is created by this gate.

Evidence preservation currently has no automatic expiry. This supersedes the earlier
30-day automatic-retention proposal: that proposal is not a current cost ceiling or
deletion policy. Versioning and prevent_destroy are not WORM or protection from an
administrator, in-place mutation, guard removal or an external cleanup principal. Storage
and noncurrent versions can grow indefinitely. A later retention/hold decision, pricing
review and exact cleanup authority must be separately approved; this gate grants none.

## AWS authenticity is still unavailable

Authenticating HashiCorp tool artifacts does not authenticate CloudTrail evidence.
AWS-shaped parsing/collection/controlled receipts still emit authenticated=false and
cannot enter trusted findings or closure. Existing archive/content hashes, bounded gzip
equality, canonical records, conflict handling and pending/invalid states are unchanged.

Future supported AWS CLI validate-logs use must reconcile original S3 locations and exact
versions, standard/backfill chains, delayed/missing/contradictory intervals, exact signed
log membership and uncompressed-content hashes, retaining compressed hashes separately.
Exit0 or an unrelated validated member is insufficient. Offline controlled outcomes can
never become authoritative signed-validation receipts. See the existing
[source-authentication design](architecture/AWS_OFFLINE_SOURCE.md).

Live-only gates remain: approved account/principals, role assumption and effective IAM/SCPs,
actual CloudTrail delivery, cost/retention/cleanup, digest/version custody and trusted
durable ingestion. No plan or AWS request is authorized by native compatibility success.
Wazuh remains NO-GO under the retained physical-memory baseline, and the historical
PostgreSQL SIGSEGV cause remains unproven. Complete existing regressions remain required;
PostgreSQL matrix suites are serialized per workflow, with no local parallel stress.

# Threat model

## Offline AWS preparation boundary

Phase1B-AWS-0 handles AWS-shaped hostile bytes and fake service observations without a network/credential client. Synthetic and AWS-shaped schemas remain distinct. Complete records, unknown fields and both hash domains are retained; a normalized projection, claimed role, JSON trust field, CLI exit0 or matching checksum cannot establish AWS authenticity.

Scope binds account, region, role unique ID/ARN, trail and exact bucket/log/digest prefixes. Acquisition rejects expired/mismatched identity before source access, malformed/error pages, escaping/regressing/repeated paired service markers, wrong owners/versions, changed current objects and batch/stream limits. Complete bounded staging precedes compare-and-swap checkpoint publication. The in-memory ledger demonstrates within-process semantics only. Source listing is not an atomic S3 snapshot. Version history/delete markers are rejected rather than skipped.

Controlled signature/chain/membership outcomes are test inputs. Even consistent outcomes stay pending and `require_authenticated` always rejects. Future supported CLI validation must cover original locations, standard/backfill chains and exact membership; no VersionId switch exists. Current-key validation cannot silently authenticate an unrelated downloaded version. Uncompressed hashes bind signed membership; compressed hashes preserve retrieval bytes separately. Missing/delayed/contradictory data and version races remain explicit gaps. No AWS-shaped result enters findings, recommendation authority or closure.

Terraform has a closed resource/IAM source allowlist and separate runtime/provisioning/cleanup identities. Structural checks cannot prove provider compatibility, effective policies, organization boundaries, service delivery or trustworthy credentials. Terraform is absent locally: executable/provider validation remains blocked. No provider initialization, plan/apply, AWS call or budget exists here. Wazuh RAM failure and the unproven historical PostgreSQL crash remain unresolved; independent offline preparation waives neither SIEM nor authenticity acceptance. See [AWS architecture](AWS_OFFLINE_SOURCE.md).

Status: target threat model, 2026-11-03. Phase 1A-1 covers [offline parsing/detection](../OFFLINE_FOUNDATION.md); Phase 1A-2 adds [local persistence and recovery controls](PERSISTENCE_CONTRACTS.md). Phase 1A-3A implements [local authentication, per-case authorization and append-only notes](ANALYST_WORKSPACE.md). Phase 1A-3B adds reviewed synthetic no-action recommendations, distinct decisions, restricted consistency verification and guarded exercise closure. Live-source trust and cloud response remain future requirements. See the [system design](SYSTEM_DESIGN.md) and [delivery gates](../DELIVERY_ROADMAP.md).

## Assets, actors and scope

Assets: private raw logs/digests, source locations, role sessions, configuration snapshots, backups, conclusions, reviewer identity, approvals, audit records, dependencies, Terraform state and the AWS bill. Read-only telemetry can expose account structure and personal data.

Adversaries include an unauthenticated local-network user; a malicious/compromised analyst; an actor generating misleading AWS events; a compromised dependency, CI job or SIEM; malicious log text targeting a browser or optional model; and operator error. Account root, local administrator and hypervisor compromise remain high-impact residual risks. Hashes do not prevent privileged deletion, and two accounts on one laptop do not establish institutional separation of duties.

Trust zones: AWS control plane, source archive, collector/parser, database/API, browser, Wazuh VM, verifier, optional AI provider, CI and public GitHub. Review changes against the [data-flow diagram](SYSTEM_DESIGN.md#deployment-and-trust-boundaries).

## Implemented local workspace boundary

Phase 1A-3A addresses hostile browser requests and malicious account actions through both HTTP checks and actual restricted PostgreSQL identities. See the [permission matrix](ANALYST_WORKSPACE.md). The normal web configuration contains no owner/maintenance/collector credential. Each account has distinct auth and data LOGIN roles bound through `SESSION_USER`; capabilities expose only named security-definer functions. Reviewer/auditor data identities cannot mutate notes, evidence, sessions or audit. No runtime identity owns objects, can create database/schema objects, can assume owner/verifier roles or receives direct table/column DML. Startup validates these restrictions and the full security catalog, including column grants and database ownership.

Passwords use reviewed bounded Argon2id parameters and protected interactive provisioning. Random opaque sessions persist only hashed tokens; disabled, expired, rotated and revoked bearers fail. Persistent finite throttle buckets and one-use pre-login/session CSRF challenges survive server restart. Per-object grants are rechecked for lists, findings, exact record variants, historical revisions and lineage; unauthorized identifiers get the same 404. New merged cases do not inherit grants. No fixture, request header, cookie role field or note can elevate source trust or authority.

Loopback-only TLS, exact HTTPS Host/Origin checks, cross-site rejection, Secure/HttpOnly/SameSite cookies, no CORS, restrictive CSP, escaped Jinja output, parameterized SQL, bounded request bodies/processing and no-store responses contain browser attacks. Generic client failures and disabled debug/access logs limit secret disclosure. Notes use a current machine revision/fingerprint, row lock, one-use nonce and atomic author-bound note/audit insertion; failure cannot partially commit. Historical evidence and findings remain immutable to runtime users.

Restore targets must revoke PUBLIC CONNECT before a no-owner/no-ACL restore; runtime connectivity returns only when security reconstruction and the original full fingerprint validate atomically. Otherwise temporarily PUBLIC security-definer helpers could expose restored data. The tested restore preserves identities, session hashes, grants, notes and audit; cluster roles/private config are separately protected and not supplied by a database dump.

Residual risks: a local administrator, maintenance superuser or full web-process/private all-account configuration compromise can impersonate configured users or bypass routine SQL controls. Individual account SQL credential theft is scoped to that identity, but it is still a credential compromise. Login throttling permits local denial of service; MFA, remote identity, host isolation, public-server hardening and cross-host recovery are absent. Truncated history/note/source projections expose their total counts; they are not completeness claims. Evidence remains synthetic and unauthenticated, accounts are a lab simulation, and containment/cloud response are absent. Human review, verification and closure apply only to the restricted synthetic no-action workflow. Security tests are not a penetration-test certification or evidence of field detection efficacy.

## Reviewed-workflow boundary

The [Phase1A-3B model](REVIEWED_WORKFLOW.md) treats every form field, analyst note and stored source string as untrusted text. Only the fixed synthetic no-action action and empty targets exist. Recommendations bind exact evidence/case/finding/rule/manifest/generation/epoch/policy; decision expiry and optimistic versions use database state. Distinct reviewers need current assignment and live sessions. Authors must retain enabled analyst/assignment authority. Current principals and all bound identities are refreshed after locks so a concurrent role/grant/enable or checker-pin change cannot leave stale authority.

Human and verifier SQL identities have disjoint writes; web roles cannot fabricate receipts and the verifier cannot approve or close. The verifier fetches originals only through a case-scoped complete-generation request, independently reconstructs qualification and connected windows, and records verified/contradicted/inconclusive as synthetic consistency only. Global conflict/incomplete context, corrupt bytes, wrong session/count/window and stale bindings cannot close. Service code/credentials and the shared bounded syntactic parser remain explicit trust boundaries, not cryptographic attestation or AWS authentication.

Normal collection and detection also use distinct restricted SQL identities. They have justified machine-column grants, no authentication/human workflow/audit reads, no direct human receipt writes and no owner/verifier role membership. A fixed machine-audit helper prevents human-looking audit kinds. The actual identity/catalog is validated rather than trusting a config role label. A compromised pipeline credential can disrupt its permitted synthetic pipeline work; it cannot acquire human approval, independent receipt or closure authority. Maintenance remains powerful and explicitly selected for operator work.

Permitted machine DML also has database-enforced transaction boundaries. Statement triggers serialize before row locks, require a server-written same-transaction batch marker for collector writes, and atomically invalidate active human authority for material worker changes. This closes the direct-SQL race where an individual pipeline credential could otherwise append an orphan original or obsolete a finding after a closure's last check. Missing/disabled mappings cannot impersonate maintenance. Only the actual maintenance database owner/superuser bypasses this protocol; no caller-set connection flag does.

New source batches atomically invalidate review authority and make closed exercises require an explicit reviewer reopen. Machine history and prior decisions stay immutable. Pipeline-first locks, one-use action tokens, latest-receipt selection and atomic domain/audit/request-consumption protect races/replay. Real restricted SQL, backend and process termination, before/after commit, audit failures, restore quarantine and actual TLS tests supply acceptance evidence. No UI-only denial substitutes for a database denial. Host/admin compromise, private all-account config compromise, single-operator duty simulation and untested cross-host recovery remain residual risks.

The current processes run as the same local operator. Separate database roles/configurations do not prevent code executing as that OS account from reading other private files. No OS-account or host sandbox for verifier credentials is demonstrated. The verifier's code/credential custody and host are trusted; database permission tests prove a stolen individual SQL credential's scope, not containment of arbitrary web-process code execution.

## Security invariants

1. Synthetic, conflicting or unverified evidence cannot become authentic through a request field, checkbox or model output.
2. Ingestion/detection roles cannot mutate cloud controls. Provisioner credentials are absent from API, SIEM and ordinary workers. Source trust also requires the system design's exact-file binding: separate compressed/uncompressed hash domains, validated digest membership and source/digest version continuity.
3. Conclusions cite supporting evidence, counterevidence, visibility interval and uncertainty. Missing telemetry is not evidence of safety.
4. A review authorizes one recommendation version; material evidence changes require review again. Cloud action is impossible in Phase 1.
5. Failed/unknown execution and verification stay visible and block closure. Never fall back to simulated success. Later bucket-flag values are enforced by the action adapter, not IAM; account-level blocking must remain beyond responder authority.
6. Public artifacts contain no real identifiers or private infrastructure details. Private raw data is never sent to a model by default.

## Deferred controls and residual exposure

Offline parser/detector tests verify bounded inputs, synthetic trust restrictions, complete-record conflicts and session separation. They do not verify the live-source, approval, durable-audit or response invariants. Host protection, disk encryption, backup security and account ownership require operator confirmation. High availability, enterprise identity, organization-wide SCPs, multi-tenancy, off-account immutable evidence and independent institutional reviewers are outside initial scope. Re-review the threat model before any deployment depends on them.

The first live gate requires hostile-input, source-spoofing, approval-replay, evidence-drift, crash-recovery and cost-bound reviews. Mutation gates additionally require action-policy and independent-verification tests. Keep raw acceptance receipts private and publish sanitized summaries only.


## Phase 1A-2 database and worker risks

New trust boundary: hostile synthetic input enters an isolated loopback PostgreSQL lab through the bounded parser. Bytea originals and derivatives commit together; database uniqueness/FKs/version and synthetic-only checks prevent routine identity/trust drift. Full-record conflicts and new evidence mark prior conclusions pending before acknowledgment. No database flag or caller field grants AWS authenticity.

Worker races use a locked generation, SKIP LOCKED claims, database-clock leases, finite attempts and claim-token fencing. Cases append revisions and bridge lineage; stale optimistic revisions fail. The offline outbox records local receipts separately from SIEM visibility and reconciles committed receipts after acknowledgment loss, including the final attempt.

Recovery verification checks raw/normalized hashes, all source references, supporting findings, reciprocal case coverage, revisions, event timelines, lineage and outbox receipts. Independent negative tests remove or corrupt these artifacts. Genuine process termination and database-session interruption complement controlled exceptions; they do not demonstrate disk/power-loss or HA resilience.

Resource controls bound compressed/expanded bytes, records, raw objects, batches, quarantine errors, leases and attempts. Docker has project-specific names, loopback publication, CPU/memory/PID limits and generated ignored credentials; ambient remote Docker/libpq routing is rejected. Test databases are retained until explicitly scoped cleanup, so repeat runs consume disk. Ordinary Docker volumes have no portable hard disk quota.

Residual risks: the local owner/admin can bypass triggers or edit storage, shared-host compromise remains possible, private credentials/dumps require OS protection, and PostgreSQL storage/WAL may exceed evidence-byte limits. Phase1A-2 alone had no authenticated analyst or independent review/closure workflow; Phase1A-3A/3B adds the restricted local synthetic capabilities described above. External SIEM receipts, live-source authenticity, power-loss guarantees and production operational efficacy remain unimplemented or unproven. See [persistence contracts](PERSISTENCE_CONTRACTS.md) and [recovery runbook](../FAILURE_AND_RECOVERY.md).

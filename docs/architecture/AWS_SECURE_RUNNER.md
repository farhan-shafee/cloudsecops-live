# Offline secure runner preparation

Phase 1B-AWS-2 prepares lifecycle, identity and resource boundaries. It supplies no live command, credentials, default SDK session, AWS client factory, authenticated-source constructor or database intake path. All public receipts say `authenticated=false`, `trusted_findings_available=false` and `closure_available=false`.

## Process and deadline boundary

`aws_runner.process.run_isolated` is an internal Python library mechanism. `WorkerRef` is trusted local code control supplied independently of bounded JSON request data. It is never taken from a browser, fixture field, AWS response or CLI argument. No generic shell or user-selected AWS operation is exposed. Future authorized assembly must use a reviewed fixed worker registry; this milestone does not activate one for AWS access.

The parent starts an independent supervisor thread that never runs worker code or SDK I/O. A Python child starts with `-I -S`, no inherited credential/proxy/profile environment, and only standard-library bootstrap code before a private gate. Containment is established before releasing the gate. Worker imports and operation execution happen afterwards. A separate reader caps length-framed JSON IPC; ordinary stdout/stderr are discarded, raw exceptions are never returned, and JSON duplicates/nonfinite values/unsupported structure fail closed.

One `monotonic()` deadline starts before validation and launch. Work stops early to reserve up to 500 ms (25% for shorter runs) for forced cleanup inside the same total budget. No new timeout is added during shutdown. Cancellation, invalid output, normal completion and exceptions all terminate the owned tree before success can be returned. A hung DNS resolver, TLS negotiation, response header/chunk parser, body read, retry or close cannot block the parent watchdog. Socket timeouts are additional controls, not the hard deadline mechanism.

Windows uses a private noninheritable Job Object with `KILL_ON_JOB_CLOSE`, no breakaway flags, verified assignment before the gate, forced termination and active-process accounting. Linux uses a new session/process group; its leader remains unreaped until the final group signal, preventing PID reuse from selecting an unrelated group. The runner checks for remaining live members before accepting success. Trusted Linux workers must keep descendants in this group: no daemonization, `setsid`, `setpgid` or arbitrary native-code execution. This is a lifecycle boundary for project code, not a sandbox against hostile same-user Python/native code. Stronger containment is required before accepting such code.

Real-time guarantees still depend on a responsive OS/kernel and scheduling. Python cannot interrupt every operating-system process-creation API. If launch is delayed beyond the deadline, the caller returns `AWS_RUNNER_SHUTDOWN_UNCONFIRMED`, with `tree_terminated=false`; a late child remains gated and the supervisor kills it without starting the operation. Unknown cleanup is a security failure, never successful evidence. It requires operator review before any future live use. See [Python timeout behavior](https://docs.python.org/3/library/subprocess.html#timeout-behavior) and [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

The child installs a numeric-loopback-only Python socket guard before worker imports. DNS, nonloopback connections and remote datagrams are denied. It permits only isolated local fault simulations. This is defense in depth for trusted Python, not an OS firewall or protection against a native dependency deliberately bypassing Python. No real AWS request is part of acceptance.

## Identity and resource authority

`IdentityAuthorization` requires the independently supplied exact `AwsScope`, a UTC `SessionLease` and explicit temporary-session provenance. Scope fixes account, `us-east-1`, IAM role ARN and immutable `AROA` identity. The assumed-role ARN and STS UserId session suffix must agree exactly. Root/admin-shaped roles, long-lived keys, absent/malformed issue/expiry, future/expired sessions and wrong immutable IDs fail. The existing adapter independently rejects refreshable/default credentials and shared-client credential substitution.

These are offline observations. A role name cannot establish its effective permissions; a harmless name might still have administrative policy. Before live execution the owner must independently approve effective IAM, boundaries/SCPs, actual temporary issuance/expiry and private credential delivery. A ChatGPT AWS connection or an operator-supplied provenance label is not that verification. No real credential is acquired or inspected here.

`BudgetPolicy` can only reduce the reviewed ceilings: 64 attempted API calls, 16 listing-page attempts, 16 nonretry service operations, 10 MiB aggregate raw response-body bytes, two retries and 30 seconds. Counts include STS and failed attempts; failures do not refund budget. `BudgetedClients` wraps the exact injected STS/S3/CloudTrail clients before `AwsSdkTransport`, reserves operation/call/page/retry capacity before dispatch and wraps raw HTTP reads before SDK parsing. Unexpected/mutating APIs, extra parameters, wrong bucket owner/prefix/trail/version and exhausted limits permanently reject the run. SDK-internal retries remain disabled. Header/chunk parsing time is bounded by the watchdog; HTTP headers/framing are not included in the response-body byte counter. Existing per-response bounds remain intact.

The only allowed operations are STS `GetCallerIdentity`; S3 `ListObjectVersions`, `HeadObject`, `GetObject`; and CloudTrail `GetTrail`, `GetTrailStatus`, `GetEventSelectors`, `GetInsightSelectors`. There is no AssumeRole, write API, bucket enumeration or arbitrary endpoint. Complete pagination, exact versions, hash domains, conflicts and source authentication remain under the existing [guarded transport](AWS_GUARDED_TRANSPORT.md) and [AWS source contracts](AWS_OFFLINE_SOURCE.md).

## AWS CLI boundary

The [CLI receipt parser](AWS_CLI_RECEIPT_CONTRACT.md) remains pinned to AWS CLI 2.37.11 and its exact verbose grammar. Pure installation-preflight contracts compare explicit owner-reviewed platform/artifact expectations, before/after hashes, bounded version text and supplied signature observations. They do not download, execute or authenticate the binary. Matching supplied observations remain unproven execution provenance.

Prepared CLI execution binds exact scope and UTC interval to fixed validation flags and bounded deadline/output. It does not invoke the CLI. CLI internal S3/key calls are outside the SDK wrapper's budget; a real CLI process needs separately reviewed credential delivery, network/call limits and actual provenance. Exit zero without exact expected membership remains insufficient. Signed standard/backfill chains, original locations, decompressed membership hashes and version continuity still require a future separately authorized acceptance. No receipt here can authorize trusted findings or synthetic closure.

## Acceptance and live blockers

Tests use fake clients and real owned processes/numeric-loopback servers. Native Windows Job and Linux group behavior runs in the existing four OS/Python validation jobs. Coverage is reported honestly, including subprocess-only and platform-specific code; mocks alone are not native containment evidence. Database acceptance remains sequential in the existing disposable hosted service. No migration, SQL privilege or retained data changes occur.

Before live work: exact-head CI/review, separately authorized read-only scope/window, an approved non-root temporary role and issuance channel, effective permissions, fixed trusted worker assembly, verified CLI/tool artifacts, private receipt custody, bounded CLI-internal API behavior, cost/retention/state/cleanup decisions and owner stop/recovery responsibility remain mandatory. Retained PostgreSQL and Wazuh capacity remain NO-GO. Offline success is not AWS authenticity, live readiness approval or deployment permission.
